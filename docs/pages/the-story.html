Why In-Memory Declarative Mutation?

The architectural motivation behind decoupling tree navigation from DOM operations.

The Problem with Direct DOM Creation

In traditional web applications, building complex components like dynamic data tables or multi-column grids often results in scattering imperative document.createElement, appendChild, and inner HTML mutations across dozens of scripts.

This tightly couples business data transformation to browser rendering engines, making unit testing difficult, causing layout thrashing, and preventing server-side or worker execution.

The Declarative Specification Solution

Instead of touching the DOM, json-write-path operates strictly on a shared in-memory dictionary of plain JavaScript objects called a registry (such as { base, spec, data }).

A build instruction simply describes:

"Locate the node in base matching JSONPath $..colgroup, traverse to children, and push the column spec."

The resulting pure JSON specification can then be handed to any renderer (DOM renderer, canvas, SVG, or virtual DOM) cleanly and deterministically.

The Decoupled 3-Act Guarantee

To maintain absolute clarity, each operation follows three non-overlapping acts:

Act 1
Resolve
Turns path spec into concrete { parent, key }
Act 2
Pick
Resolves named mutation function
Act 3
Write
Mutates parent[key] and returns registry

Each module does exactly one job. No query logic leaks into write actions, and write actions know nothing about how destination handles were found.
